# Phase 1 — Security Review (Skill: security-review) (2026-05-21)

Scope: focused pass on the three pillars of the `security-review` skill — authentication, input handling, and secrets. Findings only; no fixes, no source edits.

---

## Authentication

### Critical
- **AUTH-C1:** `requireAuth()` honors a `db.blocked=true` flag but does NOT re-check `token_version` — **File:** `lib/security.ts:62-75` — **Issue:** Middleware (`middleware.ts:250-255`) does the `tv < db.token_version` comparison, but server actions/API routes that boot through `requireAuth()` only re-read `blocked`. If a server action is reached without the middleware running (e.g. an API route hit directly that the middleware matcher excludes — `api`, `_next/static`, etc.) the JWT `tv` is never re-validated against `users.token_version`, defeating the C14H revocation guarantee for those paths — **Impact:** A stolen JWT remains usable against `/api/*` routes after an admin-forced password reset or role downgrade until natural cookie expiry (7 days).

### High
- **AUTH-H1:** Block-status cache + token-version cache 5-minute staleness — **File:** `middleware.ts:9, 99-113` (`BLOCK_CHECK_INTERVAL_MS = 5 * 60 * 1000`) — **Issue:** Admin blocks/role-changes call `invalidateBlockStatus()` (`actions/admin.ts:223, 277, 428`) only on the Node-runtime Map. The middleware runs in the Edge runtime and shares the Map by name only — in production they are independent V8 isolates (acknowledged in `lib/block-status-cache.ts:6-13`). Worst case: a blocked user can keep operating for the cached 5 minutes plus until the Edge isolate's own cache expires — **Impact:** Revocation latency up to 5 minutes for blocked/role-demoted users on multi-isolate / multi-instance deployments.
- **AUTH-H2:** Block-status check fails open on DB error — **File:** `middleware.ts:141-144, 178-182` — **Issue:** `checkUserBlocked()` returns `{ blocked: false }` on every `fetch` failure / non-200 response, and the cache is left untouched so the next request still hits the broken path. A network blip toward Supabase = silent total bypass of block enforcement (and the entire token-version gate, which rides the same DB hop) — **Impact:** If Supabase REST is briefly unreachable, blocked users transparently regain access for the duration.
- **AUTH-H3:** Per-account lockout is in-memory only — **File:** `lib/login-lockout.ts:11-15, 23` — **Issue:** Process-local Map. Each serverless cold-start / additional instance gets its own counter. An attacker can amortize attempts across cold starts or across replicas. IP-based DB limiter (`actions/auth.ts:40-57`) still applies, but its `LOGIN_MAX_ATTEMPTS = 10` per 60 s per IP is wide for botnet-driven password spraying — **Impact:** Per-account lockout is leaky on serverless; a determined attacker rotating IPs across replicas defeats it.
- **AUTH-H4:** `forgotPasswordAction` reveals existence indirectly via timing — **File:** `actions/auth.ts:401-447` — **Issue:** "Always return success" comment (line 424) is correct, but the success path is materially slower because it generates a code, runs `UPDATE users`, and sends an email (line 429-440). The not-found path returns immediately at line 425-427. An attacker can measure the difference and enumerate accounts — **Impact:** Email enumeration via response-time side-channel.

### Medium
- **AUTH-M1:** Logout proceeds even when CSRF token is invalid — **File:** `actions/auth.ts:201-225` — **Issue:** Comment acknowledges the design choice ("destroying the session is strictly safer than leaving it open"), but this means a malicious cross-site link can force-log-out a victim and the only effect is one audit-log row with `csrf: 'invalid_or_missing'`. The redirect to `/login` is intact — **Impact:** CSRF-forced-logout DoS / session-fixation setup (attacker forces logout, then a phisher's link convinces user to log into attacker's prepared session).
- **AUTH-M2:** Login error message timing leak between user-not-found and bad-password — **File:** `actions/auth.ts:115-159` — **Issue:** "user not found" returns at line 122 BEFORE the bcrypt comparison; "invalid password" returns at line 158 AFTER `verifyPassword` (bcrypt, 12 rounds, ~100-200 ms). Identical text, but ~100+ ms timing delta is observable — **Impact:** Username enumeration via response-time side-channel.
- **AUTH-M3:** `verifyEmailAction` has no rate-limit on the email-existence probe — **File:** `actions/auth.ts:327-395` — **Issue:** Path doesn't go through `checkLoginRateLimit()` and the `incr_code_attempt` counter at line 363 only fires after `user.verification_code` is already known to exist. The pre-counter branches at lines 345-359 return distinct messages for "User not found", "Email is already verified", "No verification code found", and "Verification code has expired" — **Impact:** Enumeration of which emails are registered, verified, mid-verification, or expired.
- **AUTH-M4:** `resetPasswordAction` not gated by `checkLoginRateLimit` — **File:** `actions/auth.ts:453-533` — **Issue:** Unlike `loginAction`, `registerAction`, and `forgotPasswordAction`, the reset endpoint doesn't call `checkLoginRateLimit()` against the IP bucket before doing the DB lookup. Only the per-key code-attempt counter applies (`checkCodeAttempts(resetAttemptKey)` at line 486) — **Impact:** An attacker who has obtained a leaked 6-digit code (or is guessing) is not slowed by IP-side throttling.
- **AUTH-M5:** Session JWT created during username change does not bump `tokenVersion` — **File:** `actions/profile.ts:82-88` — **Issue:** When username changes, a new JWT is minted but `tokenVersion` is omitted from `createSession()` (defaults to 0 per `lib/auth.ts:62`). If the user already had `tv > 0` from a prior password change, the new JWT silently regresses to `tv = 0` and will be revoked by middleware on the very next request — **Impact:** Self-induced logout after username change for any user who has previously changed their password.
- **AUTH-M6:** `getCSRFTokenAction` allows any authenticated user to refresh the CSRF cookie at will — **File:** `actions/auth.ts:231-235`, `lib/auth.ts:179-191` — **Issue:** Anyone with a valid session can call this and it issues a new CSRF cookie. Combined with the not-HttpOnly CSRF cookie design (acknowledged at `lib/auth.ts:170-178`), the cookie is fully harvestable from same-origin XSS. The cookie has no `__Host-` prefix — **Impact:** If even a narrow XSS exists, the CSRF token can be exfiltrated. The double-submit defense relies on `SameSite=Strict` for the actual CSRF resistance, which is fine, but cookie hygiene is weaker than it could be.

### Low
- **AUTH-L1:** Hard-coded fallback `noreply@permitforge.app` in `From:` header when `SMTP_USER` unset — **File:** `lib/email.ts:9` — **Issue:** If misconfigured prod ever runs without `SMTP_USER`, outgoing mail goes from a domain that may not be SPF-aligned — **Impact:** Verification / reset emails get spam-foldered or rejected.
- **AUTH-L2:** Default JWT `exp` of 7 days (`SESSION_MAX_AGE` in `lib/constants.ts:27`) — **File:** `lib/constants.ts:27` — **Issue:** Long session window; combined with AUTH-C1 means a leaked JWT survives a long time outside the Edge middleware path — **Impact:** Larger blast radius on JWT theft.
- **AUTH-L3:** `secureCookieDefaults()` returns `secure: false` when `NEXT_PUBLIC_DEV_INSECURE_COOKIES=1` — **File:** `lib/cookie-options.ts:26-31` — **Issue:** Env var with `NEXT_PUBLIC_` prefix is exposed to the browser by Next.js convention. The env var name implies a dev toggle but a misconfigured prod build that ships the variable would silently downgrade cookie security and the leak would be visible to clients via the public env exposure — **Impact:** Operator footgun.

## Input Handling

### Critical
- *(none observed)*

### High
- **INPUT-H1:** Chat-stream session-ownership check uses `single()` but does not apply `MAX_CONTEXT_LENGTH` to user message before LLM — **File:** `app/api/chat/stream/route.ts:90-91, 189-202` — **Issue:** Validated user input is trimmed/sliced to 500 chars (good), but the conversation-history reload (`messages.slice(-10)` line 196) joins up to 10 prior 50,000-char DB rows directly into the LLM prompt (`actions/chat-history.ts:108` caps stored content at 50k). Only the retrieved `context` is bounded by `MAX_CONTEXT_LENGTH`; the history is not — **Impact:** A user can self-poison their session history with very long messages and then trigger expensive LLM calls (prompt-token DoS / quota burn).
- **INPUT-H2:** PDF ingestion accepts arbitrary `documentId` and downloads/parses the registered PDF without re-verifying ownership of the registry row — **File:** `app/api/ingest/route.ts:54-97` — **Issue:** Admin role gates the route (line 28), but the route then trusts the `document_registry` row for `storage_path` and `file_name`. Path-derived `pdfPath = 'public/${fileName}'` (line 96) is regex-guarded to `^[a-zA-Z0-9][a-zA-Z0-9._-]*\.pdf$`, which prevents `..` traversal — adequate but worth confirming under a code audit. PDF.js itself is the larger attack surface — **Impact:** Untrusted PDF content reaches the PDF parser; PDF.js has had history of CVEs (font/JS handlers). Defense-in-depth (process isolation, parse-timeouts) is not visible in `lib/pdf-parser.ts` from this review.
- **INPUT-H3:** `messageMatches` query in `searchChatHistory` joins to `chat_sessions!inner` and filters by `user_id` — **File:** `actions/chat-history.ts:446-452` — **Issue:** This is via `createAdminClient()` (service_role, bypasses RLS). The filter is correct, but the pattern relies entirely on the client-side `eq('chat_sessions.user_id', user.id)` filter. A future refactor that removes/renames that filter would silently leak cross-user message content — **Impact:** Brittle correctness — any change here would convert into a cross-tenant data leak with no RLS fallback.

### Medium
- **INPUT-M1:** Auth checked AFTER input validation in `loginAction` — **File:** `actions/auth.ts:67-103` — **Issue:** Rate-limit check (line 67) runs first, then validation (line 76), then per-account lockout (line 89), then DB lookup. Validation runs on `formData.get('username')` cast directly to `string` without `null` check (line 72-73). If `username` field absent, `validation.error.issues[0].message` (line 83) is returned. Acceptable, but the order means an unauthenticated client can probe lockout state with an arbitrary username (the lockout-check at line 89 happens before the DB lookup). Not exploitable, but worth noting — **Impact:** Lockout-state oracle: attacker can ping a username and observe "Too many failed attempts" vs "Invalid username" to learn whether someone else is currently being attacked.
- **INPUT-M2:** Chat assistant output rendered with `ReactMarkdown` and NO DOMPurify — **File:** `components/chat/message-bubble.tsx:17-21, 83-122` — **Issue:** The CLAUDE.md states `isomorphic-dompurify` sanitizes assistant markdown in message-bubble.tsx, but the component explicitly notes (line 17-21) that DOMPurify is NOT applied. The defense relies entirely on ReactMarkdown's default escaping + the custom `a` component allow-listing http/https. This is correct for current markdown content, but any future change to add `rehype-raw` or render assistant content via `dangerouslySetInnerHTML` would immediately become an XSS sink because the assistant text is attacker-influenceable (RAG chunks come from admin-uploaded PDFs, which a compromised admin or a maliciously-named PDF could poison) — **Impact:** Fragile defense; no defense-in-depth via DOMPurify. Documentation in CLAUDE.md drifts from code.
- **INPUT-M3:** Chat message validation `sanitizeString` strips `<...>` tokens only with greedy regex — **File:** `lib/validations.ts:12` — **Issue:** `s.replace(/<[^>]*>/g, '')` does not strip nested or malformed tags (e.g. `<<script>x</script>`) — first pass leaves `<script>x` after stripping `<<script>`. Combined with the markdown render path (INPUT-M2) the residual angle brackets become text, which is safe today, but the regex is not a true HTML sanitizer despite the comment claiming XSS protection — **Impact:** Misleading naming; a future caller that trusts `sanitizeString` for HTML contexts would have a false sense of safety.
- **INPUT-M4:** `searchChatHistory` ILIKE pattern correctly escapes `%` and `_` — **File:** `actions/chat-history.ts:431` — **Issue:** Good. But the lookbehind/lookahead is absent; the snippet builder at line 476-479 uses `indexOf` on the raw query — fine — but the snippet is rendered downstream without further escaping. Should be verified the consumer escapes for display — **Impact:** Low (snippet eventually flows through React text nodes which escape). Worth a brief check.
- **INPUT-M5:** `updateBuildingDetailsSchema` accepts very wide numeric ranges — **File:** `lib/validations.ts:229-238` — **Issue:** Partial schema allows `numberOfFloors` 0-200, `totalBuiltUpArea` 0-1_000_000, `buildingHeight` 0-1000. Reasonable, but `runComplianceCheck` (`actions/permits.ts:598`) ships these to the LLM. Nothing stops a user from spamming compliance-check requests with absurd values to burn API quota (compliance check is rate-limited per-action though, line 611) — **Impact:** Bounded by rate-limit; medium because the LLM call burns real money / quota.
- **INPUT-M6:** Filename in `Content-Disposition` derived from session title with naive `replace` — **File:** `app/api/chat/export/route.ts:94` — **Issue:** `title.replace(/[^a-zA-Z0-9-_ ]/g, '').slice(0, 50).trim()` is safe against CRLF injection (no `\r\n` survives), but the route does not quote-escape backslashes in the disposition. With the regex stripping everything outside `[a-zA-Z0-9-_ ]`, the residual is already safe. OK — defensive note only — **Impact:** Currently safe; brittle if regex ever loosens.

### Low
- **INPUT-L1:** `setPermitUnderReview` validates `permitId` but then does a separate `SELECT status, user_id, project_name` before the conditional update — **File:** `actions/admin-permits.ts:197-227` — **Issue:** Race window between read and update; the update has `eq('status', 'submitted')` guard so it's safe — but the pattern is a step away from the cleaner atomic RPC used by `review_permit_atomic`. Style only — **Impact:** None today.
- **INPUT-L2:** `getAuditLogs` `actionFilter` is passed straight to the RPC — **File:** `actions/admin.ts:69-72` — **Issue:** No allow-list of action strings. The RPC is presumably safe (parameterized), but if a future RPC version interpolated the value it would be a SQL/text-injection vector — **Impact:** Defense-in-depth gap.
- **INPUT-L3:** `chatMessageSchema` minimum length is 1 — **File:** `lib/validations.ts:62-66` — **Issue:** Empty-after-trim ("   ") survives because trim happens in `sanitizeString` AFTER the `.min(1)` length check on the un-transformed value. Trivial — **Impact:** Whitespace-only messages reach the pipeline (harmless; cache hit on prior empty-ish query).

## Secrets

### Critical
- *(none observed)*

### High
- **SECRET-H1:** `lib/cookie-options.ts:18-20` reads `NEXT_PUBLIC_DEV_INSECURE_COOKIES` — **File:** `lib/cookie-options.ts:19` — **Issue:** Anything prefixed `NEXT_PUBLIC_` is bundled into the client and exposed publicly. The variable controls a server-side cookie-security decision, which is fine, but the value is now visible to any visitor — which means a misconfigured prod accidentally shipping `NEXT_PUBLIC_DEV_INSECURE_COOKIES=1` advertises the misconfiguration to attackers — **Impact:** Operator-misconfig amplification. Pure `NEXT_PUBLIC_` naming convention misuse; the value isn't itself a secret.

### Medium
- **SECRET-M1:** Error messages from Supabase echoed verbatim to clients — **File:** `actions/admin.ts:354`, `actions/documents.ts:73,82,134,153,209,240,270,280,356,407`, `actions/chat-history.ts:50,114,176,254,330,393`, `actions/ingest-pdf.ts:147,178,287`, `app/api/ingest/route.ts:153` — **Issue:** `error.message` strings from PostgREST occasionally embed SQL hints, constraint names, or table names. Not as bad as leaking actual data, but it informs an attacker which RPC failed, which column constraint tripped, which RLS policy was hit — **Impact:** Schema/structure disclosure that helps attackers craft follow-up payloads.
- **SECRET-M2:** Default `From:` address fallback hardcodes `noreply@permitforge.app` — **File:** `lib/email.ts:9` — **Issue:** Not a secret in itself, but if the domain isn't owned, mail loops back / bounces to that owner — privacy exposure. See also AUTH-L1 — **Impact:** Domain control / deliverability.
- **SECRET-M3:** `console.error` of Supabase errors throughout — **File:** broad (e.g. `lib/auth.ts:90, 142, 215, 277, 281`, `middleware.ts:122, 141, 179`, `lib/file-magic.ts` and many `actions/*`) — **Issue:** Server logs are not user-visible, but in a hosted environment (Vercel logs, log shippers) these messages can carry partial query strings, payload echoes, and the verbatim `error.message`. The codebase deliberately AVOIDS logging tokens/passwords/process.env (verified by grep — no `console.log` of `process.env` found), but the volume of raw error-string logging is high enough that secrets ending up in metadata fields would slip through — **Impact:** Defense-in-depth gap for secret-in-error scenarios.

### Low
- **SECRET-L1:** `lib/supabase-server.ts:31` comment "should NEVER have NEXT_PUBLIC_ prefix" is correct but only enforced socially — **File:** `lib/supabase-server.ts:30-39` — **Issue:** Nothing programmatically asserts that `SUPABASE_SERVICE_ROLE_KEY` was not exposed via `NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY` accidentally. A simple startup assertion would catch a critical misconfig — **Impact:** Operator footgun; defense-in-depth gap.
- **SECRET-L2:** `lib/supabase-server.ts:60-70` caches admin client as module-level singleton — **File:** `lib/supabase-server.ts:58-70` — **Issue:** Fine as written, but means a misimport from a client component WOULD throw at import time (good). Confirmed by grep: no client component imports `lib/supabase-server.ts`. — **Impact:** None today; flagged for awareness.
- **SECRET-L3:** No `.env.example` file is present — **File:** `(absent at project root)` — **Issue:** A reviewer / clone of the repo has no template of what env vars are expected. CLAUDE.md documents them but a literal `.env.example` is best practice; absent file ≠ leak, but increases probability of operators copying real keys when handing off — **Impact:** Operator hygiene.
- **SECRET-L4:** Source maps — **File:** `next.config.ts` — **Issue:** No `productionBrowserSourceMaps: true` and no override; Next.js default is to ship source maps for the browser bundle but not include sensitive server-side maps. No secret env reads on client paths were found (grep) — **Impact:** No leak observed.
- **SECRET-L5:** Audit-log report files explicitly listed in `.gitignore` — **File:** `.gitignore:46-50` — **Issue:** Good — `phase1-report.md`, `phase2-clickpath.md`, `phase2-coverage.md`, `phase2-simplify.md`, `LOCAL_NOTES.md` are excluded. Note: this audit's output file (`docs/audits/phase1-security-review.md`) is NOT in `.gitignore` and is committed by default. If quoted secrets are added here in the future, they would be committed — **Impact:** Forward-looking footgun.
